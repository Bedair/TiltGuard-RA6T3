# CLAUDE.md: TiltGuard project context

## What this is
TiltGuard is a two-wheel self-balancing robot for the All About Circuits × Renesas Robotics Design Challenge.
**The final submission is due Nov 30, 2026; we target Nov 29.** It runs on a Renesas **FPB-RA6T3**
(Cortex-M33, 200 MHz, 256 KB flash, 40 KB SRAM) fitted to an ELEGOO Tumbller V1.1 chassis
(PCB `BalanceCarRobot-PCB-V06.1`). The Arduino Nano is removed; the RA6T3 does everything.

Judging is on "technical creativity and practical value". The RA6T3 must visibly be the core.

Goals:
1. Drone-style attitude control: IMU fusion plus a cascaded angle → rate controller on a fixed 1 kHz loop.
2. AEB for an inverted pendulum. To stop, the robot must first accelerate to lean back, then brake.
   Time-to-collision comes from the HC-SR04.
3. An automotive-style safety monitor: tilt limit, sensor timeouts, plausibility checks, battery undervoltage,
   and a defined safe state. Use the hardware PWM cut-off (POEG) where possible.

The owner is an embedded/ADAS engineer (AUTOSAR, ISO 26262). Write production-quality embedded C, not
Arduino-style code.

## Toolchain
- e² studio with **FSP 6.6.0**, GCC (GNU ARM Embedded), **bare metal, no RTOS**, flat (non-TrustZone) project.
- The project lives directly in `firmware/` (`configuration.xml`, `src/`, `ra/`, `ra_gen/`, `ra_cfg/`, `script/`).
- Debug and flash through the on-board J-Link OB (USB connector J8).
- Telemetry goes over **SEGGER RTT**, not UART.

## Hard rules
- **Never hand-edit `ra/`, `ra_gen/` or `ra_cfg/`.** They are generated by the FSP configurator from
  `configuration.xml`. When a peripheral or pin change is needed, tell the user exactly what to set in the
  FSP configurator (stack, property, value), then write the code in `src/` against the generated instances.
- Application code goes in `src/` (entry point `hal_entry.c`). Keep modules small: `imu`, `encoders`,
  `ultrasonic`, `battery`, `motors`, `control`, `safety`, `telemetry`.
- No dynamic memory allocation. No blocking calls inside the 1 kHz control ISR.
- Check every FSP API return value (`fsp_err_t`). Errors feed the safety monitor.
- Default to safe states: motors disabled (STBY low) at boot and on any fault.

## Electrical facts (verified from ELEGOO's schematic BalanceCarRobot-SCH-V06 and the stock firmware)
See `docs/hardware-findings.md` and `docs/wiring.md` for detail.
- The battery is 2S 18650 (7.0–8.4 V) on net `VM`. **The robot board has no 5 V regulator.** 5 V now comes
  from a buck converter (set to 5.0 V) fed from `VM`, through terminal-block boards (ElectroCookie on the
  FPB side, GERUI on the robot side) that replaced the original jumper wires. **The FPB itself is still
  USB-powered**, separate from the robot's 5 V rail — for untethered running later, the plan is a diode-OR
  (1N5819) from the buck converter's output into the ElectroCookie 5 V rail.
- The TB6612FNG and 74LVC2G14 run at 5 V, so the RA6T3's 3.3 V outputs are below their VIH. Motor control
  lines (PWMA, PWMB, AIN1, BIN1, STBY) go through BSS138 level-shifter modules — LV side on FPB 3.3 V, HV
  side on the buck converter's output, GND shared with the FPB.
- RA6T3 5 V-tolerant pins: P100, P101, P205, P206, P400, P401, P407–P411. All other pins are 3.3 V max.
  (Encoders, Echo, and SDA/SCL are wired direct, no shifter, because their pins are on this list.)
- **Never connect `VM` (the battery net) to any FPB pin.** Never connect the FPB's A4/A5 to SDA/SCL — on
  this board A4/A5 are plain analog pins, not the I2C bus (the ElectroCookie shield has separate dedicated
  SDA/SCL terminals) — connecting them together would short two unrelated signals.
- The encoders are single-channel: A only. M2A = left, M1A = right. Direction comes from the motor command.
  30:1 gearing, 660 pulses per wheel revolution counted on both edges (ELEGOO's figure; matches hardware
  bring-up, pending a proper driven-distance measurement in Phase 2 — see `docs/hardware-findings.md`).
- Battery sense: 10 k / 1.5 k divider, so V_bat = V_adc × 11.5 / 1.5. Full ≈ 1.10 V at the pin.
- The MPU-6050 sits at I2C address 0x68 (WHO_AM_I register 0x75 should return 0x68).

## Sign conventions (also printed at boot)
- **Forward** = the side of the robot that faces forward when it drives with pwm > 0. Defined by the motor
  driver mapping (AIN1/BIN1 low = forward, as stock) and checked by eye with the console's `jog <pct>`.
- **angle > 0 = tilted forward. pwm > 0 = wheel driven forward** (logged as `FWD`).
- **Correct balance behaviour: tilted forward → both wheels drive forward**, moving under the falling body.
- Verification, from the RTT log alone: with the speed loop off (`skp 0` + `ski 0`, or define `BALANCE_SPEED_LOOP_OFF`; the boot default is now the stock speed PI),
  the firmware checks every armed step with |angle − setpoint| > 2° and counts wheels not commanded in the
  direction of (angle − setpoint) as `sign_err` (steps where the D/turn terms are ≥ half the P term are not
  checked; there an opposite direction is correct). Dry-run (`dry 1`; off at boot, `BALANCE_DRY_RUN_AT_BOOT`)
  runs and logs the full law with the motors held off. See `tools/telemetry/README.md`.
- **S1 (as stock):** set the robot on the floor (resting on its stand is fine) and press S1 in READY: it arms
  within +/-22 deg of the setpoint, the angle term kicks it upright, and it balances (speed loop soft-starts after
  0.5 s). S1 while armed disarms; after a fall (FAULT) one S1 resets and stands it up ~0.5 s later. The wheels-lifted motor self-test
  is no longer on S1; `jog <pct>` on the console still runs it.
- Every armed 40 ms window says whether each wheel turned (`mot L=ok`/`NONE`/...); ~0.5 s driven at >= 30%
  with no encoder edges latches FAULT `0x4` (`SAFETY_FAULT_ENCODER`).

## Stock firmware baseline (ELEGOO Tumbller, to port first and then beat)
- 200 Hz loop, Kalman angle filter, balance PD kp = 55 / kd = 0.75, angle_zero = 0.
- Speed PI kp = 10 / ki = 0.26, run every 8th cycle (40 ms), integral clamped to ±3000.
- Turning kd = 0.5 on the yaw rate. `kp_turn = 2.5` is declared but **never used**.
- Motors cut out beyond **±22°** (the ±27° values in the source are commented out).
- IMU: ±250 dps / ±2 g, DLPF 260 Hz (power-on default; `mpu.initialize()` never writes CONFIG).
  `Gyro_z = -gz / 131` is integer division (truncated to whole deg/s), with no bias removed.
- Ported in `src/control/balance.{c,h}`; that header lists every deliberate difference.
- Battery thresholds: full above 7.8 V, low below 7.0 V.
- The stock gains are in 8-bit PWM units at about 490 Hz. Rescale them for the RA6T3's PWM resolution.

## Safety while developing
- Phase 1 ran with the battery switch OFF; the FPB's USB powered the robot's 5 V rail directly.
- Phase 2 (terminal-block boards) needs the battery ON to feed the buck converter — `VM` only ever goes
  into the buck converter's IN+, never into any FPB pin, and the FPB's own logic stays on USB power
  throughout, electrically separate from the robot's 5 V rail.
- Never connect `VM`, or the empty Nano socket's `VIN`, to any FPB pin. Never connect the FPB's A4/A5 to
  SDA/SCL (see Electrical facts above).
- When the motors are first enabled, keep the robot lifted (wheels free) and add a firmware tilt cut-off.
