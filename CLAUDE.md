# CLAUDE.md: TiltGuard project context

## What this is
TiltGuard is a two-wheel self-balancing robot for the All About Circuits × Renesas Robotics Design Challenge.
**The final submission is due Nov 30, 2026; we target Nov 29.** It runs on a Renesas **FPB-RA6T3**
(Cortex-M33, 200 MHz, 256 KB flash, 40 KB SRAM) fitted to an ELEGOO Tumbller V1.1 chassis
(PCB `BalanceCarRobot-PCB-V06.1`). The Arduino Nano is removed; the RA6T3 does everything.

Judging is on "technical creativity and practical value". The RA6T3 must visibly be the core.

Goals:
1. Drone-style attitude control: IMU fusion plus a cascaded angle → rate controller on a fixed 1 kHz loop.
2. AEB for an inverted pendulum. To stop, the robot must first accelerate to lean back, then brake.
   Time-to-collision comes from the HC-SR04.
3. An automotive-style safety monitor: tilt limit, sensor timeouts, plausibility checks, battery undervoltage,
   and a defined safe state. Use the hardware PWM cut-off (POEG) where possible.

The owner is an embedded/ADAS engineer (AUTOSAR, ISO 26262). Write production-quality embedded C, not
Arduino-style code.

## Toolchain
- e² studio with **FSP 6.6.0**, GCC (GNU ARM Embedded), **bare metal, no RTOS**, flat (non-TrustZone) project.
- The project lives directly in `firmware/` (`configuration.xml`, `src/`, `ra/`, `ra_gen/`, `ra_cfg/`, `script/`).
- Debug and flash through the on-board J-Link OB (USB connector J8).
- Telemetry goes over **SEGGER RTT**, not UART.

## Hard rules
- **Never hand-edit `ra/`, `ra_gen/` or `ra_cfg/`.** They are generated by the FSP configurator from
  `configuration.xml`. When a peripheral or pin change is needed, tell the user exactly what to set in the
  FSP configurator (stack, property, value), then write the code in `src/` against the generated instances.
- Application code goes in `src/` (entry point `hal_entry.c`). Keep modules small: `imu`, `encoders`,
  `ultrasonic`, `battery`, `motors`, `control`, `safety`, `telemetry`.
- No dynamic memory allocation. No blocking calls inside the 1 kHz control ISR.
- Check every FSP API return value (`fsp_err_t`). Errors feed the safety monitor.
- Default to safe states: motors disabled (STBY low) at boot and on any fault.

## Electrical facts (verified from ELEGOO's schematic BalanceCarRobot-SCH-V06 and the stock firmware)
See `docs/hardware-findings.md` and `docs/wiring.md` for detail.
- The battery is 2S 18650 (7.0–8.4 V) on net `VM`. **The robot board has no 5 V regulator.** 5 V came
  from the Nano. It is now supplied by the FPB's 5 V (bench, battery OFF) or a buck converter (later).
- The TB6612FNG and 74LVC2G14 run at 5 V, so the RA6T3's 3.3 V outputs are below their VIH.
  **Motor control lines must go through the 3.3 V → 5 V level shifters (Phase 2).**
- RA6T3 5 V-tolerant pins: P100, P101, P205, P206, P400, P401, P407–P411. All other pins are 3.3 V max.
- The encoders are single-channel: A only. M2A = left, M1A = right. Direction comes from the motor command.
  30:1 gearing, about 660 pulses per wheel revolution counted on both edges, as the stock firmware does.
- Battery sense: 10 k / 1.5 k divider, so V_bat = V_adc × 11.5 / 1.5. Full ≈ 1.10 V at the pin.
- The MPU-6050 sits at I2C address 0x68 (WHO_AM_I register 0x75 should return 0x68).

## Stock firmware baseline (ELEGOO Tumbller, to port first and then beat)
- 200 Hz loop, Kalman angle filter, balance PD kp = 55 / kd = 0.75.
- Speed PI kp = 10 / ki = 0.26, run every 8th cycle.
- Turning kp = 2.5 / kd = 0.5.
- Motors cut out beyond ±27°.
- Battery thresholds: full above 7.8 V, low below 7.0 V.
- The stock gains are in 8-bit PWM units at about 490 Hz. Rescale them for the RA6T3's PWM resolution.

## Safety while developing
- Phase 1 runs with the battery switch OFF; the FPB's USB powers the robot's 5 V rail.
- Never connect `VM`, or the empty Nano socket's `VIN`, to any FPB pin.
- When the motors are first enabled, keep the robot lifted (wheels free) and add a firmware tilt cut-off.
